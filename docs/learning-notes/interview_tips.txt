Taints & Tolerations.
-------------------------

node selector -> controls where a pod can go.
Taint -> controls which pods are allowd onto a node. (Don't schedule pods here unless they are permitted.)

Tolerations -> Gives a Pod permission to tolerate a matching taint.
Taint on node ---matches ----- Tolerations on pod.

kubectl taint nodes prod-cluster-worker3 workload=database:NoSchedule
what does Noschedule mean?
Ans -> kubernetes will not schedule new pods onto the node unless they tolerate the taint.

it does not automatically evict existing pods.

There are three main effects:
NoSchedule -> Don't schedule new non-tolerating pods
PreferNoSchedule -> Try to avoid scheduling them
NoExecute -> don't schedule + can evict existing non-tolerating pods.

important interview concept:
A toleration does not force a pod onto a node. it only says 
This pod is allowed to run there.

The scheduler can still choose another suitable node.

usecase:
if you want only database pod should run on worker 3
the use both :
taint, tolerations and node selector.

Q-> you have dedicated database node. how would you prevent normal application pods from being scheduled there ?
Ans -> I would apply a taint such as workload=database:NoSchedule to the node. only pods with the corrosponding tolerations can be scheduled there. if i want database pods specifically 
on that node, i would additionally use a node label with node selector or node affinity.

pod anti-affinity HA concept
==========================
imagine frontend replicas are placed on node 1
and if node 1 dies , then all your replicas for frontend will be die 
so, that's bad HA.

We can tell kubernetes:
Don't place replicas of this application on the same node.

That's pod anti-affinity.

Q-> Difference between node affinity and pod anti-affinity?
Ans -> Node affinity controls pod placement based on node labels, whereas pod anti-affinity controls 
pod placement based on the other pods. For ex -> node affinity can place a workload on SSD nodes, 
while pod anti-affinity can distribute replicas across different nodes for high availability.

Q- What is the difference between pod anti-affinity and topology spread constraints?
Ans -> 
pod anti-affinity can prevent pods from being placed together based on other pod labels, while topology
spread constraints provide more explicit control over how evenly pods are distributed across topology domains
such as nodes or availability zones.

- Node drain
- Cluster upgrades
- Kubernetes administrator evicting Pods

ResourceQuota :- controls the total resources used by the namespaces

LimitRange :- controls default/min/max resources for individual containers.

limitRange 
==========
apiVersion: v1
kind: LimitRange
metadata:
  name: task-platform-limits
  namespace: task-platform

spec: 
  limits:
    - type: Container
      default: 
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: 128Mi

Scope:
Applies to containers inside pods in the task-platform namespace.

default:
If you don’t specify resource limits in your pod spec, Kubernetes will automatically assign:

CPU limit = 500m (half a CPU core)

Memory limit = 512Mi (512 MB)

defaultRequest:
If you don’t specify resource requests in your pod spec, Kubernetes will automatically assign:

CPU request = 100m (0.1 CPU core guaranteed)

Memory request = 128Mi (128 MB guaranteed)

RequestQuota
===============
apiVersion: v1
kind: ResourceQuota
metadata:
  name: task-platform-quota
  namespace: task-platform
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    pods: "10"

requests.cpu: "2"  
→ Across all pods in the namespace, the total CPU requests cannot exceed 2 cores.
(Requests = guaranteed minimum CPU the scheduler reserves.)

requests.memory: 2Gi  
→ Across all pods, the total memory requests cannot exceed 2 GiB.
(Requests = guaranteed minimum memory reserved.)

limits.cpu: "4"  
→ Across all pods, the total CPU limits cannot exceed 4 cores.
(Limits = maximum CPU a pod can use if available.)

limits.memory: 4Gi  
→ Across all pods, the total memory limits cannot exceed 4 GiB.
(Limits = maximum memory a pod can use before being OOMKilled.)

pods: "10"  
→ You can only create up to 10 pods in this namespace.




A pod’s request must be ≤ limit.

QoS Classes
============================
1. Guaranteed
Condition: Every container in the pod has equal CPU and memory requests = limits.
Effect: Pod gets the highest priority. It’s the last to be evicted under resource pressure.
Example:
yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

2. Burstable
Condition: Pod has requests < limits, or some containers specify requests while others don’t.

Effect: Pod gets medium priority. It’s guaranteed its request, but can burst up to its limit if resources are free.

Example (your case):

yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
→ This pod is Burstable because request (100m) < limit (500m).

3. BestEffort
Condition: Pod has no requests or limits defined at all.

Effect: Pod gets the lowest priority. It can use resources opportunistically, but is the first to be evicted under pressure.

Example:

yaml
resources: {}


============================
Requests = guaranteed slice of CPU/memory.

Limits = maximum burst allowed.

Quota enforcement:

Kubernetes checks requests first.

If your pod requests exceed the quota (e.g., 3 CPUs > 2 CPUs quota), admission fails.

Even though the namespace allows up to 4 CPUs in limits, you can’t reach that unless your requests are within the quota.

⚙️ How to Actually Use Full Limits
You can only hit the limit quota (4 CPU, 4Gi) if:

Your requests stay ≤ 2 CPU and ≤ 2Gi (namespace quota).

Your limits can then be set higher (up to 4 CPU, 4Gi).

👉 Example pod that works:

yaml
resources:
  requests:
    cpu: "1.5"
    memory: "1.5Gi"
  limits:
    cpu: "3"
    memory: "3Gi"
Requests (1.5 CPU, 1.5Gi) fit under quota (2 CPU, 2Gi).

Limits (3 CPU, 3Gi) fit under quota (4 CPU, 4Gi).

✅ Pod admitted, can burst up to 3 CPU/3Gi.
